# Проверка подключения и устранение неисправностей

Проверяйте по слоям: локальный listener → TCP до VPS → REALITY/VLESS → DNS и загрузка → маршрутизация приложений. Не меняйте сразу несколько параметров: после каждого изменения повторяйте один и тот же запрос.

## Ошибка 404 при загрузке установочного архива

Если установка остановилась на `Downloading Xray archive` с HTTP 404, до настройки VLESS дело ещё не дошло. Ответ 404 означает отсутствие запрошенного ресурса на ответившем сервере; это не признак закрытого входящего порта 443 на VPS.

31.10.2026 для прежнего `v26.10.29` повторно подтверждён 404 и через API, и по адресу архива. API сообщает стабильный `v26.10.31`; файл `Xray-linux-64.zip` этого релиза отвечает HTTP 200. Продолжить установку можно так:

```bash
bash /root/xray-install.sh install --version 26.10.31
/usr/local/bin/xray version
```

Либо пусть официальный установщик сам определит текущую стабильную версию:

```bash
bash /root/xray-install.sh install
```

В [примечаниях к 26.10.31](https://github.com/XTLS/Xray-core/releases/tag/v26.10.31) авторы сообщают, что отозвали 26.10.29 при выпуске срочного обновления безопасности: в новом релизе по умолчанию отключён MPTCP из-за проблемы в ядре Linux. Они также рекомендуют обновить само ядро. Не используйте сохранённый архив отозванной версии для обхода этой ошибки. Актуальный список — [GitHub Releases API](https://api.github.com/repos/XTLS/Xray-core/releases/latest). Правила UFW, SSH и ключи REALITY менять не требуется.

Если новая ссылка также возвращает 404 именно с вашего VPS, проверьте цепочку ответов:

```bash
curl -IL --max-time 30 \
  https://github.com/XTLS/Xray-core/releases/download/v26.10.31/Xray-linux-64.zip
```

Обычно GitHub отвечает перенаправлением, затем сервер файлов — HTTP 200. Если диагностика показывает другой результат, сохраните коды и заголовки ответа, сведения о HTTP-прокси и результате запроса API. Не отключайте проверку HTTPS (`-k`) как способ исправления 404.

## Предупреждение REALITY: Choosing ... as the target

Если после предупреждения написано `Configuration OK.`, конфигурация принята. Это не сообщение о состоявшейся блокировке и не проверка доступности target. В версии 26.10.31 условие применяется к строкам `serverNames`: суффиксы `.ru`, `.ir`, `.cn` или подстроки `apple`, `icloud`, `microsoft` после приведения к нижнему регистру. [Исходный код проверки](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/transport_security.go#L157-L163).

`rutube.ru` вызывает предупреждение из-за окончания `.ru`, а не из-за отдельного анализа RuTube. GFW в тексте означает китайскую систему фильтрации; текущую доступность из российской сети проверяйте реальным подключением.

Для начального сравнения можно проверить `www.kernel.org`, `www.debian.org`, `www.mozilla.org` командами TLS из раздела 4. Выбирайте доступный с VPS узел с TLS 1.3, HTTP/2, подходящим сертификатом и небольшими задержками. Согласованно измените серверные `target`/`serverNames` и клиентский SNI, проверьте конфиг и перезапустите службу. Ключи и UUID для замены target менять не требуется.

## 1. Не работает даже localhost-прокси

Если curl сообщает `Failed to connect to 127.0.0.1`, сначала проверьте, запущено ли ядро и какой порт реально указан в настройках.

Windows:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 10808
```

Linux:

```bash
ss -ltnp 'sport = :10808'
```

При `address already in use` порт занят другим VPN-клиентом или второй копией Xray. Завершите ненужную копию либо задайте другой локальный порт и измените его в приложениях. Не открывайте localhost-прокси в firewall VPS: он находится на клиентском ПК.

## 2. Доступен ли TCP-порт VPS

Windows:

```powershell
Test-NetConnection SERVER_IP -Port 443
```

Linux:

```bash
nc -vz -w 5 SERVER_IP 443
```

На VPS:

```bash
systemctl --no-pager --full status xray
ss -ltnp 'sport = :443'
ufw status verbose
journalctl -u xray -n 100 --no-pager
```

| Наблюдение | Что проверить дальше |
|---|---|
| Нет listener на VPS | Ошибка JSON, путь `ExecStart`, занятый порт, права `root:xray 0640` |
| `Connection refused` | Достигнутый узел отвергает соединение; проверьте listener и REJECT-правила |
| Timeout из всех сетей | IP VPS, firewall хостинга, UFW/nftables, работоспособность VPS/маршрута |
| С домашнего интернета работает, с мобильного нет | Ограничения или проблема маршрута конкретного оператора; сравните другую сеть |
| TCP проходит, HTTPS через прокси нет | Переходите к проверке REALITY/VLESS |

Вывод о блокировке нельзя делать по одному timeout: так же выглядит неисправный сервер и неверное правило firewall. Открытый TCP-порт не проверяет UUID и ключи.

## 3. REALITY не проходит авторизацию

Сопоставьте поля вручную:

| Сервер | Клиент |
|---|---|
| `settings.users[].id` | UUID / `settings.id` |
| `users[].flow: xtls-rprx-vision` | Точно такой же flow |
| `realitySettings.serverNames[]` | `serverName` / SNI |
| `privateKey` | Соответствующий `Password (PublicKey)`, в URI `pbk` |
| `shortIds[]` | Один из этих `shortId`, в URI `sid` |
| `raw + reality`, порт 443 | `tcp/raw + reality`, адрес именно VPS и порт 443 |

Частая ошибка — клиентский `pbk` взят из другой генерации `xray x25519`, перепутан с `Hash32` или содержит приватный ключ. На сервере можно заново вывести соответствующий клиентский ключ:

```bash
xray x25519 -i 'ВАШ_PRIVATE_KEY'
```

Значение нужно вводить в приватной серверной сессии: буквальный ключ может остаться в истории оболочки. Для регулярной работы храните реквизиты в защищённых файлах шага 6 серверной инструкции.

Сообщение `REALITY: received real certificate (potential MITM or redirection)` часто означает, что соединение попало в обычный fallback, потому что REALITY-авторизация не состоялась. Оно само по себе не доказывает MITM. Проверьте ключ, short ID, SNI, порт и fingerprint.

В [issue Xray #7259](https://github.com/XTLS/Xray-core/issues/7259) есть свежий разбор несовместимости `edge` и некоторых других fingerprint с серверами `26.9.x/26.10.x`; для исходной проверки используйте `chrome` и актуальный официальный Xray. Нельзя считать произвольное переключение fingerprint гарантированным обходом фильтрации. Патчи сторонних форков в базовой инструкции не используются.

Short ID должен содержать hex-символы `0–9`, `a–f` и иметь чётную длину до 16 символов. Пример генерации `openssl rand -hex 8` выдаёт нужные 16 символов. Сверка: [официальные поля REALITY](https://xtls.github.io/en/config/transports/reality.html).

## 4. Доступен ли target с VPS

Подставьте выбранное имя:

```bash
TARGET_SERVER_NAME='www.kernel.org'
getent ahosts "$TARGET_SERVER_NAME"
xray tls ping "$TARGET_SERVER_NAME:443"
openssl s_client -connect "$TARGET_SERVER_NAME:443" \
  -servername "$TARGET_SERVER_NAME" -tls1_3 -alpn h2 \
  -verify_hostname "$TARGET_SERVER_NAME" \
  -verify_return_error </dev/null
```

Ошибка DNS target или отсутствие TLS-соединения с ним на VPS требует исправить серверную сеть/DNS либо выбрать другой подходящий target. Если сервер сообщает предупреждение о неудачном выборе target, не игнорируйте его: проверьте [критерии REALITY](https://github.com/XTLS/REALITY/blob/main/README.en.md) и используйте другого кандидата.

При замене target согласованно обновляйте `target`, `serverNames` и клиентский SNI. UUID и ключи при этом менять не обязательно. Сохраните предыдущую рабочую конфигурацию.

## 5. Маленький запрос проходит, страницы зависают

Сначала подтвердите HTTPS и затем передачу хотя бы 1 МБ. Можно скачать начало официального архива Xray с ограничением диапазона. Некоторые серверы игнорируют `Range`, поэтому фактически может скачаться весь архив около нескольких десятков МБ.

Windows:

```powershell
curl.exe --max-time 60 --location --fail --range 0-1048575 --proxy socks5h://127.0.0.1:10808 --output NUL --write-out "HTTP=%{http_code} bytes=%{size_download} speed=%{speed_download}\n" https://github.com/XTLS/Xray-core/releases/download/v26.10.31/Xray-linux-64.zip
```

Linux:

```bash
curl --max-time 60 --location --fail --range 0-1048575 \
  --proxy socks5h://127.0.0.1:10808 --output /dev/null \
  --write-out 'HTTP=%{http_code} bytes=%{size_download} speed=%{speed_download}\n' \
  https://github.com/XTLS/Xray-core/releases/download/v26.10.31/Xray-linux-64.zip
```

Если сервер поддерживает диапазон, ожидается HTTP 206 и 1048576 байт; HTTP 200 с полным файлом также показывает передачу данных. Проверяйте не только код, но и объём/завершение без timeout.

Если примерно одинаковый малый объём проходит, затем соединение каждый раз замирает только у одного оператора, сравните тот же клиент/конфиг в другой сети. В [первичном обсуждении измерений net4people](https://github.com/net4people/bbs/issues/490) описаны ограничения передачи, SNI и IP-подсетей. Это диагностическая гипотеза, которую нужно подтвердить сравнением, а не универсальный признак любой блокировки.

Практический порядок действий:

1. На VPS проверьте обычную загрузку без прокси, нагрузку и лимит трафика у хостинга.
2. Проверьте тот же клиент из другой сети.
3. Проверьте резервный VPS в другой сети/ASN, если доступен.
4. Только при подтверждённой фильтрации SNI проверяйте другой корректный target/SNI.
5. Если RAW/REALITY в этой сети стабильно не работает, рассмотрите отдельный резервный профиль с другим транспортом, например [XHTTP](https://github.com/XTLS/Xray-core/discussions/4113), с собственной согласованной настройкой сервера и клиента.

Переименование `tcp` в `raw`, смена UUID и повторная генерация ключей не меняют доступность заблокированного IP. При разрешении только отдельных подсетей нужен реально достижимый узел. При полном отсутствии канала до внешней сети настройка Xray связь не создаст.

## 6. SOCKS работает, браузер или другое приложение нет

Если команда `curl --proxy socks5h://…` успешна:

- проверьте активный системный прокси/ручной прокси браузера;
- убедитесь, что выбран правильный локальный порт и активный профиль;
- для приложений, игнорирующих прокси, включите TUN;
- временно проверьте Global, затем верните нужные исключения;
- проверьте DNS и IPv6, а также конфликт с другими VPN;
- проверьте, не направляют ли готовые правила нужный сайт напрямую.

На Xray-клиенте `socks5h` передаёт имя серверу; `socks5` обычно разрешает его локально. Поэтому успех первого при ошибке второго полезен для диагностики DNS.

При TUN проверяйте запрос без прикладного прокси:

```bash
curl --noproxy '*' --max-time 20 https://api.ipify.org
```

На Windows используйте `curl.exe` и двойные кавычки вокруг `*`. Сравните внешний IP. Если приложение всё равно выходит напрямую, смотрите исключения, policy routing, IPv6 и правила маршрутизации.

## 7. DNS и IPv6

Один успешный IP-тест не доказывает отсутствие DNS/IPv6-утечек. Для проверки:

1. В SOCKS-браузере включите удалённое разрешение DNS.
2. В TUN проверьте штатную настройку DNS-перехвата и выход DNS по туннелю.
3. Если есть IPv6, отдельно проверьте IPv6-выход. При политике «весь интернет через VPS» он не должен оставаться прямым у провайдера.
4. Сравните с сетевым захватом на физическом интерфейсе, если требуется точное подтверждение маршрута DNS.

В Linux команда `resolvectl status` информативна только при использовании systemd-resolved; она не показывает автоматически DNS внутри каждого приложения. В Windows `ipconfig /all` также описывает системную конфигурацию, а не все запросы приложения.

Не меняйте глобально DNS и не отключайте IPv6 во всей системе в качестве первого действия: сначала локализуйте, какой путь даёт ошибку. При отсутствии IPv6-выхода у VPS можно выбрать IPv4 для разрешения назначения или настроить блокирование IPv6 в TUN, если такая политика вам подходит.

## 8. Какие данные сохранять для разбора ошибки

Запишите версии приложения/ядра/сервера, дистрибутив, провайдера и тип сети, результат TCP-теста, результат SOCKS HTTPS-теста, объём перед остановкой и короткий фрагмент ошибки из журнала. Отметьте, работает ли тот же профиль через другого оператора.

Перед передачей логов удалите UUID, ключи, ссылку доступа, IP/домены, которые не хотите раскрывать. На VPS для короткой диагностики можно временно установить `loglevel: info` и перезапустить службу, затем вернуть `warning`. Подробные логи могут содержать адреса назначений.

После аварийного завершения клиента сначала восстановите обычный доступ: отключите оставшийся системный прокси и TUN через приложение, отмените переменные прокси в терминале. Изменения серверного firewall не исправляют оставшийся прокси `127.0.0.1` на компьютере.
